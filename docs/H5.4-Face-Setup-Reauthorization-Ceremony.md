# H5.4: HAPI-owned Face Setup reauthorization ceremony

## Why

H5.3D-4 traced a production `UNAUTHORIZED` on
`GET /v1/authenticators/privateid/status` to Base44's `getAccessToken()` presenting a
cached/stale HAPI access token: HAPI access tokens are opaque, Redis-backed, and
expire after five minutes (`ACCESS_TOKEN_TTL_MS`), but nothing guarantees Base44
refreshes that token before Bookwrm later asks a user to set up Face. `/v1` correctly
rejected the stale bearer; it is not weakened by this change.

H5.4 removes the dependency on any Bookwrm/Base44-held token for Face setup
entirely. Bookwrm only redirects the browser to a new HAPI-owned entry point; HAPI
mints fresh canonical authority itself, in-process, via a brand-new H4 email OTP
round trip, immediately before FACE_AUTH_V1 consent and PrivateID enrollment.

## Ceremony

```
Bookwrm authenticated user
      |
GET /face-setup/start?client_id=...&return_uri=...
      |
HAPI Email authentication (H4, one OTP) -- reuses InteractiveEmailAuthentication
      |
canonical ACTIVE HAPI_EMAIL subject resolved and re-verified
      |
certified pilot allowlist check (keyed by resolved oidc subject, never email)
      |
FACE_AUTH_V1 consent (Not Now / Agree & Continue)
      |
HapiFaceEnrollmentService.acceptConsent + start (same H5.2 service/repository)
      |
PrivateID enrollment, browser return via /face-setup/callback
      |
302 redirect to the registered Bookwrm return URI with only ?face_setup=outcome
```

No token, PUID, IdentitySubject ID, or biometric data ever appears in the redirect.
The ceremony is a thin orchestration layer: it calls the existing
`HapiFaceEnrollmentService` (`acceptConsent`/`start`/`status`/`capabilityStatus`) and
`InteractiveEmailAuthentication` (H4/H6) directly, in-process, rather than making
HTTP calls back into `/v1`. The existing `/v1` routes
(`GET/POST /v1/authenticators/privateid/*`) are untouched and remain the
authoritative API for any other authenticated HAPI-owned caller.

## Transaction model

`FaceSetupInteractionStore` (`src/authenticators/FaceSetupInteractionStore.ts`) is a
Redis-backed, purpose-bound (`FACE_SETUP`), single-ceremony record mirroring
`AuthorizationInteractionStore`'s browser-handle pattern:

- an opaque 256-bit handle is set as an `HttpOnly; Secure; SameSite=Lax` cookie
  scoped to `/face-setup`;
- the record itself (`clientId`, `returnUri`, CSRF token, phase, timestamps, and —
  only once minted — the H5 `FaceEnrollmentAuthority` and enrollment binding) is never
  exposed to the browser;
- a fixed 10-minute absolute expiry is set at creation and never extended by `save()`;
- every state-changing POST is rejected unless its `csrf` field matches the
  interaction's CSRF token (`FaceSetupInteractionStore.csrfMatches`, constant-time).

## Authentication and canonical subject binding

`/face-setup/email` and `/face-setup/email/code` reuse H4/H6's
`InteractiveEmailAuthentication` exactly as Universal Login does: `start()` must
return mode `AUTHENTICATION` (never `REGISTRATION`/`INELIGIBLE`) or the ceremony
fails without ever creating an `IdentitySubject`. After a single successful OTP
verification, the ceremony independently re-resolves the canonical subject via
`IdentityRegistry.findByOidcSubject(principal.sub)` and requires
`primaryProvider === "HAPI_EMAIL" && status === "ACTIVE" && emailVerified === true &&
email === primaryProviderSubject` — the OTP result alone is not sufficient
authority, matching H5's own `requireRecentEmailAuthority` policy.

Only after that re-verification does the ceremony check the certified pilot
allowlist (`HAPI_FACE_SETUP_PILOT_SUBJECTS`, a comma-separated set of canonical
`oidcSubject` values configured out-of-band), keyed on the resolved subject — never
on the client-supplied email or a Base44 user id.

## Return URI

`return_uri` must be one of the Bookwrm OIDC client's already-registered
`redirectUris` (the same closed allowlist used for OIDC authorization requests).
There is no separate open-redirect surface and no new config list to keep in sync.

## Consent and enrollment

The consent screen is the same HAPI Face consent copy
(`FACE_AUTH_CONSENT_TEXT`/`FACE_AUTH_CONSENT_VERSION`/`FACE_AUTH_CONSENT_PURPOSE`
from `FaceEnrollmentTypes.ts`). "Not Now" clears the interaction with zero service
calls — no consent record, no enrollment. "Agree & Continue" calls
`acceptConsent()` then `start()` on the same H5 service, preserving every H5.2
guarantee (conflict protection, idempotency, concurrency protection, subject
binding, atomic finalization, revoked-authenticator policy) unmodified.

### Duplicate submission hardening (H5.4C-3)

Consent POSTs validate CSRF before phase handling, then revalidate the canonical
HAPI_EMAIL pilot subject, recent email authority, client and exact return URI.
Redis atomically compares the complete loaded snapshot before claiming
`CONSENT -> STARTING`. Only the winner accepts consent and starts enrollment.
Concurrent or repeated valid submissions redirect with `303` to the server-owned
`/face-setup/continue` route; they never clear the interaction or repeat mutations.
While the winner is working, that route renders a bounded polling page. Once
`ENROLLING` is persisted, it reuses the provider launch URL retained only in the
server-side interaction. No additional provider identifiers enter browser state.

Every interaction save is compare-and-set and caps its TTL by both the existing
Redis TTL and the original absolute deadline. Persistence failure produces a safe
failure page, never a provider launch or success redirect. A claim is not released
or automatically retried after an uncertain failure: this avoids repeating
already-committed consent or provider operations. The existing enrollment lifetime
is unchanged. Completed/cancelled ceremonies remain non-resumable.

The consent page also disables both buttons and prevents repeat submission after
the first valid form submit, using a nonce-authorized script. Server-side atomic
claiming remains authoritative if JavaScript is absent or bypassed.

Lifecycle diagnostics allow only event/request ID, cookie/interaction presence,
interaction state, coarse remaining TTL, reason code and HTTP status. No handles,
CSRF/OTP/token values, email, subjects, PUIDs, provider transactions or biometrics
are logged. Missing, invalid and consumed state use generic continuation-failure
copy; expiry copy is used only when a stored deadline proves expiration. Once
Redis has naturally removed a record, expiry versus loss is unknown and is not
reported as proven expiry. Consumed markers last no longer than the original TTL.

This patch does not repair or dispose of the first production pilot's persisted
consent, expired pending enrollment or binding. That remains a separate controlled
operation; patch certification does not authorize a production retry or deployment.

## Expired-enrollment recovery (H5.4C-5)

FACE_AUTH_V1 authorizes FACE_AUTHENTICATION for the canonical subject and its
tenant/application/client context, not an individual enrollment transaction.
The consent schema has no enrollment foreign key or enrollment-relative expiry;
reservation and capability checks use the exact purpose/version/context. An
expired enrollment does not invalidate that consent. Acceptance is idempotent
under the canonical subject lock and preserves the existing acceptance evidence.

After fresh H4 email authentication and the canonical pilot checks, H5.4 recognizes
existing consent and starts enrollment through the same atomic submission claim,
without showing or writing duplicate consent. Missing/current-version or
different-context consent still requires the affirmative consent screen. All
Redis persistence checks, CSRF and duplicate-submit protections remain in force.

Expired transactions and their transaction-specific bindings remain history.
Fresh reservation generates a new enrollment ID, provider transaction and binding
to the same canonical subject. The old binding is not reused or rewritten, and
late completion of the expired transaction fails closed. Subject locking ensures
concurrent fresh ceremonies create only one new pending enrollment/provider session.

The existing capability contract reports a prior expired enrollment as `FAILED`
(there is no separate `EXPIRED` capability enum). With current consent, no active
Face authenticator, and fresh eligible HAPI_EMAIL authority, it reports
`consentRequired=false`, `faceEnrollmentEligible=true`, `faceLoginEligible=false`.
There is no separate `retryAllowed` field: eligibility is conditional on fresh H4,
enabled features and current canonical/H1 authority.

No production cleanup, provider call, deployment or live retry is authorized by
this local recovery certification.

### Duplicate OTP continuation hardening (H5.4C-7)

Consent reuse can advance directly from the OTP POST to `STARTING` and `ENROLLING`.
Repeated OTP POSTs must not consume that interaction merely because it has left
`EMAIL`. After CSRF and the existing canonical subject, pilot, freshness, client
and return URI checks, they redirect with `303` to `/face-setup/continue`, without
re-verifying OTP, accepting consent, reserving enrollment or creating a provider
session. If consent is still required, they redirect to the existing consent page
without accepting it. Stale GETs of the code page use the same authority-checked
continuation. Invalid requests fail closed without clearing a valid enrollment;
consumed or cancelled ceremonies cannot resume.

The controlled second live attempt reached a fresh enrollment and binding, then
a repeated OTP POST consumed its valid `ENROLLING` interaction. The next OTP POST
rendered continuation-failure copy with `COOKIE_MISSING`. This is an HAPI
continuation lifecycle defect, not proven initial cookie loss or malformed
Bookwrm handoff. Local regression coverage reproduces the repeated OTP sequence
and checks in-flight continuation, CSRF/authority rejection and terminal state.
The local patch does not authorize deployment, record repair or another live retry.

### Ceremony replay audit (H5.4C-8)

| Browser endpoint | Classification | Replay behavior |
| --- | --- | --- |
| Email submit | ATOMIC/SINGLE-CLAIM | One challenge per interaction; duplicates use the existing code page. |
| OTP verification | ATOMIC/SINGLE-CLAIM | One verification/result consumption at a time; advanced duplicates resume consent or enrollment. |
| Email resend | ATOMIC/SINGLE-CLAIM | Concurrent sends are single-claimed; later explicit resends retain H4 cooldown/rate-limit policy. |
| Consent | ATOMIC/SINGLE-CLAIM | Existing snapshot claim protects acceptance and enrollment reservation. |
| Enrollment continuation | IDEMPOTENT | Read-only processing/launch continuation; never reserves again. |
| Browser callback | TERMINAL/REPLAY-SAFE | Pending polls preserve state; only the matching snapshot can consume terminal state. Premature callbacks cannot cancel setup. |
| Provider finalization | ATOMIC/SINGLE-CLAIM | Existing PostgreSQL subject/enrollment locks and provider-evidence checks preserve exactly-one attachment and reject conflicting/expired replays. |
| Cancel | TERMINAL/REPLAY-SAFE | Requires the form's CSRF; snapshot-checked consumption cannot erase newer state. A cancelled ceremony cannot resume. |

Email operations use a server-only `emailOperation` claim with the existing
Redis snapshot compare-and-set and absolute deadline. Concurrent requests poll the
code page instead of repeating side effects. Expected verification/delivery
rejections release the claim through checked persistence; unexpected errors leave
uncertain work claimed rather than automatically repeating it.

Stale email-page GETs, email POSTs and resend POSTs use the same authority-checked
advanced continuation as OTP replays. Early consent GETs and callbacks reject
invalid phases without consuming the ceremony. All terminal consumption compares
the loaded snapshot atomically, including cancellation and callback races.
This release does not repair enrollment history or authorize an automatic live retry.

Release certification runs all regression suites, including the eight PostgreSQL
suites against separate local test databases to avoid cross-suite schema/fixture
interference. H5 recovery regressions repeat both OTP and consent POSTs against the
real repository and prove one new enrollment, binding and mocked provider session
with original consent and expired history retained. The complete matrix passes
548 tests in 62 files with zero failures or skips; the production build and diff
check also pass. Provider tests use mocks only, never the live PrivateID service.

## Feature flag and pilot gate

`HAPI_FACE_SETUP_ENABLED` (default disabled) gates the entire `/face-setup/*`
surface; when disabled every route responds `404`. `HAPI_FACE_SETUP_PILOT_SUBJECTS`
remains empty by default, so no subject is eligible until explicitly certified.
Enabling H5.4 does not itself enable Base44 Face mutation; that gate is unchanged
and remains a separate decision.
