# H6.11 Bookwrm Universal Login UX

H6.11 adds a client-aware, server-rendered Bookwrm theme for the
`bookwrm-base44-production` Universal Login client. Other clients keep the existing HAPI
presentation. The brand definition uses a fixed server-side client allowlist, escaped copy,
validated color tokens, and a static inline Bookwrm mark; client identifiers cannot supply
HTML, CSS, or script.

The Bookwrm email screen introduces the account-security step and the OTP screen presents
the next progress step. OTP entry remains a single native form control with the existing
input constraints, autocomplete, paste behavior, CSRF field, and submit-once guard. The
resend form and the server's existing limits and challenge validation are unchanged.

Registration and authentication use the same pre-verification copy. Showing a returning-user
message, a registration-specific message, or an email hint before successful verification
would disclose whether an address is registered. No email hint is currently carried by the
authorization interaction, so the page uses neutral inbox copy instead.

The successful verification handler still issues the existing `303` OIDC callback redirect
without an intermediate success page or additional delay. No authentication, challenge,
interaction, redirect, or OIDC claim semantics are changed.

## H6.11.1 zero-choice landing

For `bookwrm-base44-production`, the landing page shows the Bookwrm mark, welcome
heading, neutral "Let's get you securely into your account." copy, and exactly one
**Continue** button when Email is available. It uses the existing `GET /login/email`
form: viewing the chooser or continuing to Email creates no challenge and sends no OTP.
Step 1 shows "Confirm your email" and **Send My Code** without the former extra
account-security introduction. Step 2 and its submit-once/resend behavior are unchanged.

Bookwrm Face is unavailable in this release, including with
`HAPI_FACE_ENROLLMENT_ENABLED=false`. H5 and the legacy Face routes are unchanged;
other HAPI clients retain their existing chooser. Turning H5 on alone does not offer
Face to every Bookwrm user. The renderer accepts an explicit `faceAvailable` capability
for future integration, but no current Bookwrm route opts in. A future server-side caller
must certify the client/release capability and returning-user enrollment before enabling
that choice; the renderer does not infer capability from code existence or browser input.
