# HAPI ID H6.8 — Unified Universal Login Email

Universal Login's single Continue with Email journey supports new and returning
HAPI_EMAIL users without exposing the internal branch in the browser.

## Server-side flow

After the existing H1 client authority is resolved, Universal Login normalizes
the submitted address and checks both canonical email claims and the
`HAPI_EMAIL` primary-provider key:

| Identity state | H2 purpose | Completion |
| --- | --- | --- |
| Exactly one ACTIVE, verified HAPI_EMAIL subject for the authorized application | `AUTHENTICATION` | Existing H4 verification/result handoff |
| No subject claims the normalized email | `REGISTRATION` | H2 proof, then H3 completion |
| Any non-eligible claimant or multiple claimants | `AUTHENTICATION` | Verify and consume the proof, then return generic failure |

The ineligible branch never invokes H3. A PrivateID identity is not merged,
rewritten, or used to create a second HAPI_EMAIL subject. H3 remains responsible
for atomic registration, one canonical subject under concurrent registration,
registration evidence, provenance, and collision rejection.

For successful registration, the internal continuation principal is created
from the H3-established subject only after H3 completes. Registration proof
replay is rejected. The principal exists only on the server and only within the
existing short-lived Universal Login interaction.

Both successful branches consume the original AuthorizationInteraction once
and issue the ordinary authorization code using its saved redirect URI, state,
nonce, scopes, tenant/application binding, and PKCE challenge. No second
`/authorize` request or OTP is introduced.

## Browser and telemetry

All branches use the same email-entry form, redirect to the same code-entry
page, and use the same generic failure presentation. The OTP email content is
purpose-independent. Identity classification and branch values are retained
server-side; no account-existence, provider, subject count, challenge purpose,
or registration terminology is returned in the browser.

Safe lifecycle events distinguish `EMAIL_FLOW_STARTED`,
`EMAIL_AUTHENTICATION_COMPLETED`, `EMAIL_REGISTRATION_COMPLETED`, and
`EMAIL_FLOW_FAILED`. They contain no email, OTP, verification ID,
authentication result, interaction handle, token, or provider subject.
Classification adds an identity lookup before H2 start, so the branches are not
claimed to be cryptographically constant-time; they share the same user-facing
responses and email delivery path to avoid an obvious account-enumeration
signal.

H4's trusted API contract and eligibility rules are unchanged. H5, Face
enrollment, legacy identities, Base44, and production state are not modified by
this flow.
